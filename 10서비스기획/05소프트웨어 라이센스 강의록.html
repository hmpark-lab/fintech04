1. 학습 개요와 목표

이 강의는 오픈소스와 오픈소스 라이선스의 기본 개념을 이해하고, 주요 라이선스의 종류와 범위를 구분하며, 실제 개발에서 라이선스를 어떻게 확인하고 어떤 점을 지켜야 하는지를 익히는 데 목적이 있다.

학습목표

  1. 저작권과 오픈소스의 개념을 이해한다.
  2. 주요 오픈소스 라이선스의 종류 및 범위를 이해한다.
  3. 오픈소스 라이선스 확인 방법과 코드 작성 시 준수사항을 이해한다.

핵심 용어

  • 오픈소스 라이선스: 저작권자의 독점 사용 권리에 대해 사용자에게 허용되는 이용방법과 조건 범위를 명시한 사용 허가권
  • Permissive 라이선스: 의무가 비교적 단순한 라이선스
  • Copyleft 라이선스: 파생저작물 배포 시 더 강한 공개·동일 라이선스 의무를 부과하는 라이선스

2. 저작권과 오픈소스 라이선스

2-1. 오픈소스의 개념

오픈소스는 저작권자가 소프트웨어를 개발한 뒤 특정 규정, 즉 라이선스 조건에 따라 소스코드를 공개하여, 다른 사람이 관련 정보에 접근하고, 2차 저작물을 생성하고, 수정하고, 배포할 수 있도록 한 소프트웨어를 말한다.

  • 오픈소스의 핵심은 무료가 아니라 자유로운 사용 가능성이다.
  • Free & Open Source Software에서 Free는 가격이 0원이라는 뜻이 아니라 사용·수정·배포의 자유를 의미한다.
  • 저작권자가 소스코드를 공개하더라도 저작권 자체를 포기한 것은 아니다.
  • 모든 소프트웨어는 원칙적으로 저작권자의 보호를 받으며, 오픈소스는 그 권리를 특정 조건 아래 허락하는 방식이다.

2-2. 오픈소스와 상용 소프트웨어의 차이

오픈소스

  • 소스코드 제공
  • 사용, 복제, 배포, 수정 가능
  • 기술지원에 별도 비용이 들 수 있음
  • 프리웨어와 동일 개념이 아님

상용 소프트웨어

  • 대부분 실행파일(Binary) 위주 제공
  • 바이너리 수준의 이용 중심
  • 복제, 수정, 재배포는 일반적으로 제한
  • 프리웨어는 상용 소프트웨어 중 무료 사용 가능한 형태일 수 있음

2-3. 오픈소스의 법적 책임

오픈소스도 상용 소프트웨어와 마찬가지로 라이선스를 반드시 준수해야 한다. 라이선스를 위반하면 사용 권리가 박탈될 수 있고, 해당 코드를 포함한 제품의 판매가 제한될 수 있다. 또한 커뮤니티나 권리자로부터 클레임을 받아 기업 이미지에 손실이 발생할 수도 있다.

중요한 오해 바로잡기

“오픈소스니까 아무렇게나 써도 된다”는 생각은 잘못이다. 오픈소스는 자유를 주지만, 그 자유는 라이선스 조건 안에서만 보장된다.

2-4. 오픈소스 라이선스의 의미

오픈소스 라이선스는 저작권자의 독점 사용 권리에 대해, 저작권자와 사용자 사이의 이용방법과 조건 범위를 명시해 둔 사용 허가권이다. 즉, 라이선스 문서에는 크게 두 가지가 들어 있다.

  • 이용 조건: 이 오픈소스로 무엇을 할 수 있는가
  • 의무 사항: 사용할 때 무엇을 지켜야 하는가

라이선스는 저작권자가 직접 만들 수도 있지만, 현실적으로는 MIT, BSD, Apache, GPL, LGPL, AGPL처럼 이미 널리 사용되는 표준 라이선스 중 하나를 선택하는 경우가 많다.

2-5. Public Domain

아무 제한 없이 사용할 수 있는 Public Domain도 존재한다. 이는 원 저작물에 대해 저작권자가 권리를 포기하거나 기부했거나, 저작권 보호기간이 끝났거나, 법령이 특정 저작물의 저작권 소멸을 규정한 경우를 뜻한다.

  • 저작물 변경 가능
  • 출처 표시 의무가 없는 경우가 많음
  • 저작권자와 협의 없이 재배포 가능
  • 상업적 용도로도 사용 가능

주의

저작권자가 불분명하다고 해서 Public Domain으로 간주하면 안 된다. 권리관계가 불명확한 경우는 반드시 별도로 확인해야 한다.

3. 오픈소스 라이선스의 의무사항

오픈소스를 사용할 때 항상 같은 의무가 생기는 것은 아니지만, 강의 자료에서 공통적으로 강조한 일반적 의무는 고지, 소스코드 공개, 동일 라이선스 적용이다.

3-1. 저작권 표시 및 라이선스 고지

대부분의 오픈소스 라이선스는 개발자·기여자·저작권에 관한 사항을 제품에 표시하거나 포함하도록 요구한다. 또한 이용자가 권리 내용을 이해할 수 있도록 라이선스 사본을 함께 첨부하도록 요구하는 경우가 많다.

  • 원저작자 표시
  • 저작권 문구 유지
  • 라이선스 전문 또는 사본 제공
  • 필요 시 NOTICE 등 부가 고지문 포함

3-2. 소스코드 공개

모든 라이선스가 소스코드 공개 의무를 가지는 것은 아니다. 그러나 대표적으로 GPL 계열은 바이너리 형태 배포를 허용하는 대신, 그 바이너리에 대응하는 소스코드를 함께 공개할 것을 요구한다.

3-3. 재배포 시 동일 라이선스 적용

GPL을 대표로 하는 Copyleft 라이선스는 소프트웨어를 수정한 뒤 배포할 경우, 수정된 파생저작물도 동일한 라이선스로 배포할 것을 요구한다.

3-4. 의무가 발생하는 시점

자료에서는 이러한 의무사항이 주로 오픈소스를 이용해 만든 파생저작물을 회사 외부로 배포할 때 발생한다고 설명한다. 여기서 배포란 소스코드나 바이너리 코드의 복제본을 다른 사람이나 다른 회사에 제공하는 행위를 뜻한다.

재배포하지 않는다면?

예를 들어 사내 테스트 용도나 내부 사용 목적의 서비스에서만 활용하고 외부로 배포하지 않는다면, 강의 자료 기준으로는 이런 의무가 부과되지 않는 것으로 설명한다.

4. 주요 오픈소스 라이선스

4-1. 전체 구도

자료에 따르면 오픈소스 라이선스는 전 세계적으로 매우 많지만, 실제 사용은 상위 소수의 라이선스에 집중된다. 또한 소스코드 공개 의무의 강도에 따라 크게 Permissive 라이선스와 Copyleft 라이선스로 나눌 수 있다.

4-2. Permissive 라이선스

Permissive 라이선스는 의무사항이 많지 않아 상대적으로 준수하기 쉬운 라이선스이다. 일반적으로 저작권 표시, 라이선스 고지 같은 고지 의무를 지키면 된다.

MIT 라이선스

  • MIT에서 공학도들을 돕기 위해 개발한 라이선스
  • BSD 라이선스에 기반
  • 소스코드 공개 의무가 없음
  • 라이선스 및 저작권 명시가 필요
  • 저자나 저작권자는 소프트웨어에 대해 책임을 지지 않는다는 면책 조항을 둠
  • 예시: Node.js, jQuery, Ruby on Rails, X11, VS Code

실제 사례 (직접 확인)

  • GitHub (React - MIT)
    https://github.com/facebook/react/blob/main/LICENSE
    역할: 사용자 인터페이스(UI)를 만들기 위한 JavaScript 라이브러리로, 웹 프론트엔드 개발에서 가장 널리 사용되는 기술 중 하나이다.

Apache 라이선스

  • Apache 재단의 소프트웨어에 적용되는 대표적 라이선스
  • 소스코드 공개 의무는 없음
  • 라이선스와 버전 표기를 요구하는 점이 강조됨
  • 실무적으로는 고지 의무를 꼼꼼히 챙겨야 함

실제 사례 (직접 확인)

  • GitHub (TensorFlow - Apache 2.0)
    https://github.com/tensorflow/tensorflow/blob/master/LICENSE
    역할: 머신러닝과 딥러닝 모델을 개발하고 학습시키기 위한 대표적인 AI 프레임워크이다.
  • AI 모델 (Sentence Transformers - Apache 2.0)
    https://github.com/huggingface/sentence-transformers/blob/main/LICENSE
    역할: 문장을 벡터(임베딩)로 변환하여 검색, 추천, 유사도 비교 등 NLP 작업에 사용하는 AI 모델 라이브러리이다.
  • PyPI (sentence-transformers)
    https://pypi.org/project/sentence-transformers/
    역할: Python 환경에서 Sentence Transformers 모델을 쉽게 설치하고 사용할 수 있도록 제공하는 패키지이다.

BSD 라이선스

  • Berkeley Software Distribution 계열 라이선스
  • Permissive 성격의 대표 라이선스
  • 소스코드를 공개하지 않아도 됨
  • 저작권 표시 및 라이선스 고지가 핵심 의무

실제 사례 (직접 확인)

  • GitHub (NumPy - BSD)
    https://github.com/numpy/numpy/blob/main/LICENSE.txt
    역할: Python에서 행렬 연산과 수치 계산을 수행하기 위한 핵심 라이브러리로, 대부분의 데이터 분석 및 AI 라이브러리의 기반이 된다.
  • PyPI (Flask - BSD-3-Clause 계열)
    https://github.com/pallets/flask/blob/main/LICENSE.txt
    역할: Python으로 웹 서버와 API를 간단하게 만들 수 있는 경량 웹 프레임워크이다.

4-3. Copyleft 라이선스

Copyleft 라이선스는 Permissive보다 의무가 복잡하고 까다롭다. 핵심은 파생저작물을 배포할 때 동일한 라이선스로 유지해야 한다는 점이다.

Copyleft는 Copyright의 반대말처럼 보이지만, 저작권을 부정하는 개념이 아니라 오히려 저작권을 기반으로 정보 공유를 강화하려는 자유 소프트웨어 운동의 철학을 담고 있다.

GPL 라이선스

  • 가장 널리 알려진 Copyleft 라이선스
  • 배포 시 해당 바이너리 전체의 소스코드 공개 의무가 강하게 적용됨
  • GPL 오픈소스를 사용해 만든 파생 프로그램도 Copyleft 라이선스를 따라야 함
  • 자료에서는 정적·동적 링킹 여부와 관계없이 강하게 적용되는 것으로 설명함

여기서 링킹(Linking)이란 외부 라이브러리를 프로그램에 연결하는 방식을 의미하며, 크게 정적 링킹과 동적 링킹으로 나뉜다.

  • 정적 링킹: 컴파일 시 라이브러리 코드가 프로그램 내부에 포함되어 하나의 실행파일로 결합되는 방식
  • 동적 링킹: 실행 시 외부 라이브러리를 불러와 사용하는 방식으로, 프로그램과 라이브러리가 분리되어 존재함

일반적으로 정적 링킹은 라이브러리 코드가 프로그램에 포함되므로 라이선스 영향을 강하게 받으며, 동적 링킹은 라이브러리를 분리하여 사용하는 방식이지만 GPL의 경우에는 이 또한 파생저작물로 간주될 수 있어 라이선스 적용을 신중히 검토해야 한다.

실제 사례 (직접 확인)

  • GitHub (Linux Kernel - GPLv2)
    https://github.com/torvalds/linux/blob/master/COPYING
    역할: 운영체제의 핵심인 커널로, 하드웨어와 소프트웨어를 연결하고 시스템 자원을 관리한다.

LGPL 라이선스

  • GPL보다 완화된 라이선스
  • 오픈소스를 수정하거나 정적 링킹하여 사용하면 공개 의무가 발생할 수 있음
  • 원본 그대로 동적 링킹으로 사용하는 경우는 비교적 자유도가 높다고 설명함
  • 단, 일부 코드를 복사해 사용하는 경우에는 공개 의무를 따라야 할 수 있음

실제 사례 (직접 확인)

  • GitHub (FFmpeg - LGPL)
    https://github.com/FFmpeg/FFmpeg/blob/master/LICENSE.md
    역할: 영상과 오디오를 변환, 인코딩, 디코딩하는 멀티미디어 처리 라이브러리이다.

AGPL 라이선스

  • 가장 방어적인 Copyleft 라이선스 중 하나
  • 네트워크와 상호작용하는 소프트웨어의 소스코드까지 공개 의무를 확장
  • 웹서비스를 통해 서비스를 제공하는 것도 배포로 간주하는 관점이 강하게 반영됨
  • 서버 측 소스코드 공개 의무까지 고려해야 함

실제 사례 (직접 확인)

  • GitHub (Odoo Community - LGPL v3)
    https://github.com/odoo/odoo/blob/16.0/LICENSE
    역할: 기업의 회계, 재고, CRM 등을 관리하는 ERP(기업 관리 시스템) 플랫폼이다.
  • OCA 모듈 (AGPL 예시)
    https://github.com/OCA/server-tools/blob/16.0/LICENSE
    역할: Odoo 기능을 확장하기 위한 커뮤니티 모듈로, 다양한 기업 기능을 추가로 제공한다.

4-4. CCL (Creative Commons License)

자료에는 소프트웨어 라이선스 외에 이미지나 문서 같은 창작물에 적용되는 CCL도 함께 소개되어 있다. 이는 일정 조건 아래 타인에게 이용을 허락하는 라이선스이다.

  • BY: 저작자 표시
  • NC: 비영리, 영리 목적 사용 불가
  • ND: 변경 금지
  • SA: 동일 조건 변경 허락, 2차 저작물에도 동일 라이선스 유지

특히 SA는 소프트웨어 라이선스의 Copyleft와 유사한 성격으로 설명할 수 있다.

5. 주요 라이선스 비교표

구분 소스코드 공개 의무 대표 라이선스 핵심 의무 및 특징
Permissive 없음 또는 매우 약함 MIT, Apache 2.0, BSD, ISC 주로 저작권 표시와 라이선스 고지 의무를 지키면 사용 가능. 상업적 활용과 결합이 상대적으로 자유로움.
약한 Copyleft 조건부 LGPL, EPL, Artistic License 수정하거나 정적 링크 등 특정 방식으로 결합하면 공개 의무가 생길 수 있음. 원본 그대로의 동적 사용은 비교적 유연.
강한 Copyleft 강함 GPL 2.0, GPL 3.0, AGPL 배포 시 사용 소스 공개, 동일 라이선스 유지 의무가 강함. AGPL은 네트워크 서비스 제공까지 고려해야 함.
Public Domain 없음 퍼블릭 도메인 저작물 권리 포기, 보호기간 만료, 법령상 소멸 등의 경우 자유 사용 가능. 단, 권리 불명확 저작물과 혼동하면 안 됨.
한 줄 요약
소스코드를 공개하고 싶지 않다면 Permissive 쪽이 상대적으로 안전하고, 공개와 동일 라이선스 유지가 핵심인 Copyleft는 사용 범위를 더 신중히 검토해야 한다.

6. 오픈소스 라이선스 확인 방법

6-1. 직접 확인하는 방법

대부분의 오픈소스 패키지, 저장소(GitHub 등), 프로젝트 홈페이지, 기술문서에는 라이선스 정보를 담은 파일이 포함되어 있다.

  • 최상위 디렉토리에서 LICENSE, COPYING 같은 파일을 찾는다.
  • 소스코드 상단의 라이선스 헤더를 확인한다.
  • 프로젝트 문서나 홈페이지의 라이선스 안내를 읽는다.

다만 이 방법은 인력이 적고, 팀 내 오픈소스 라이선스 교육이 충분히 선행된 경우에 적합하다. 사람이 수작업으로 확인하면 휴먼에러가 생길 수 있기 때문이다.

6-2. 오픈소스 검사 소프트웨어 활용

대규모 팀이나 기업에서는 검사 솔루션을 활용해 라이선스 위반 여부를 점검한다. 자료에서는 크게 세 가지 방식이 소개된다.

  1. 소스코드 내부 문자열 검색
  2. 실제 소스코드 내용을 스캔해 오픈소스 코드와 비교
  3. 소스코드 없이 바이너리를 스캔해 사용된 오픈소스 확인

6-3. 라이선스 확인이 어려운 경우

라이선스를 찾을 수 없다고 해서 저작권이 없는 오픈소스라고 판단해서는 안 된다. 가장 바람직한 방법은 저작권자나 권리자의 연락처를 찾아 문의해 확인하는 것이다.

7. 코드 작성 시 유의사항

7-1. 고지문 작성

대부분의 오픈소스는 사용 시 고지문 작성을 요구하므로, 제품이나 문서에 “이 프로그램은 오픈소스를 사용했다”는 점을 명시하고, 문의 연락처와 사용한 오픈소스 목록을 빠짐없이 적는 것이 중요하다.

7-2. 전체 파일 구조를 포함하여 사용

함수 몇 개만 복사해 사용하는 방식보다, 가능한 한 디렉토리 단위로 사용하고 원본 구조를 유지하는 것이 권장된다. 그래야 나중에 어떤 오픈소스를 사용했는지 추적하기 쉽다.

  • 원본 프로젝트명과 디렉토리 구조를 최대한 유지한다.
  • 구조 유지가 어렵다면 최소한 LICENSE, README 파일은 포함한다.
  • 일부 코드만 발췌해 쓰면 라이선스 추적과 검증이 어려워진다.

7-3. 3rd Party 코드의 분리 관리

회사가 저작권을 소유하지 않은 코드나 데이터 파일은 별도의 디렉토리로 관리하는 것이 권장된다. 예를 들면 /external, /reference 같은 폴더가 있다.

이렇게 분리해 두면 나중에 라이선스 검토와 컴플라이언스 점검을 훨씬 쉽게 할 수 있다.

8. 위반 사례와 실무 해석

8-1. 라이선스 위반 사례

PlayStation 2 게임 ICO 사례. 2007년 11월 Alexander Stranger가 게임 텍스처를 역분석한 결과, GPL로 배포된 libarc 라이브러리 일부가 사용된 것이 발견되었던 사례.

자료의 요지는 다음과 같다.

  • GPL 소스코드를 사용해 제작한 소프트웨어를 상용 판매할 경우
  • 해당 소프트웨어 전체를 GPL로 배포하고
  • 소스코드를 공개해야 하는 의무를 이행해야 한다

이에 따라 SONY가 전체 소스코드를 공개했고, 결국 2008년 2월에 생산이 종료되었다.

8-2. 실무적으로 기억할 점

개발자 관점

“패키지 설치만 했는데 괜찮겠지”라고 넘기지 말고, 배포 형태와 결합 방식, 수정 여부, 서비스 제공 방식까지 함께 검토해야 한다.

팀/회사 관점

오픈소스 목록 관리, 고지문 작성, 외부 코드 분리, 검사 도구 도입 같은 체계를 미리 만들어 두는 것이 가장 강력한 예방책이다.

9. 최종 정리

  1. 오픈소스는 누구나 자유롭게 사용·수정·재배포할 수 있도록 공개된 소프트웨어이지만, 이는 라이선스 조건 안에서만 가능하다.
  2. 오픈소스 라이선스는 저작권자의 독점 사용 권리를 사용 허가의 형태로 조정하는 법적 장치이다.
  3. 주요 라이선스는 크게 Permissive와 Copyleft로 구분되며, 핵심 차이는 소스공개와 동일 라이선스 유지 의무의 강도이다.
  4. MIT, Apache, BSD는 비교적 유연하고, GPL, LGPL, AGPL은 파생저작물 공개와 배포 방식에 더 민감하다.
  5. 오픈소스를 사용할 때는 반드시 라이선스를 확인하고, 고지문 작성, LICENSE 보존, 외부 코드 분리 관리 등 실무 절차를 갖춰야 한다.
